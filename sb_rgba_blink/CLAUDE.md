# sb_rgba_blink

An FPGA example project for the Lattice iCE40 UP5K (iCEBreaker board) that blinks the onboard RGB LED.

## Overview

This project uses the iCE40's built-in hard IP blocks (no external clock or LED resistors needed) to produce a slow color-cycling blink pattern on the RGB LED.

## Files

- **blink.v** - Verilog source: the entire design
- **blink.pcf** - Pin constraint file mapping `rgb[0..2]` to physical pins 39, 40, 41 (the iCEBreaker RGB LED)
- **Makefile** - Build flow using the open-source iCE40 toolchain

## Beginner's Guide to blink.v

If you are new to FPGAs and Verilog, this section walks through every part of `blink.v` so you can understand exactly what is happening and why.

### What This Design Does (The Big Picture)

The iCEBreaker board has a single RGB LED on it — one component that can produce red, green, and blue light independently. This design makes that LED blink through different color combinations by turning each color on and off at a different speed. The result is a slowly shifting color pattern.

Unlike software (where a program runs instructions one after another), an FPGA configures actual hardware circuits. Everything in this file describes circuits that all run **simultaneously**, not sequentially.

### Line-by-Line Walkthrough

#### Preamble (lines 1–11)

```verilog
`default_nettype none
```

This is a safety setting. In Verilog, if you make a typo in a wire name, the language will silently create a new 1-bit wire for you instead of giving an error. `default_nettype none` disables that behaviour so typos become compile errors. It is considered best practice.

#### Module Declaration (lines 13–15)

```verilog
module blink (
    output wire [2:0] rgb,
);
```

A **module** is the fundamental building block in Verilog — think of it like a function definition, except it describes a piece of hardware rather than a sequence of instructions.

- `blink` is the name of the module (and the top-level design).
- `output wire [2:0] rgb` declares a 3-bit output bus called `rgb`. The `[2:0]` means it has three individual wires: `rgb[0]`, `rgb[1]`, and `rgb[2]`. These three wires connect to the red, green, and blue pins of the onboard LED (via the pin constraint file).
- `output` means this signal leaves the chip. `wire` means it is a simple connection (as opposed to a `reg`, which can store a value).

#### Internal Signals (lines 17–19)

```verilog
reg [27:0] cnt;
wire rgb_pwm[2:0];
wire clk;
```

These are signals that exist only inside the chip — they are not connected to any physical pin.

- **`cnt`** is a 28-bit **register** (a flip-flop chain). It stores a number that will count upward. 28 bits can hold values from 0 to 268,435,455 (about 268 million). It is declared as `reg` because its value is assigned inside an `always` block (see below).
- **`rgb_pwm`** is an array of three 1-bit wires. Each one will carry the on/off PWM signal for one color channel (red, green, blue).
- **`clk`** is a single wire that will carry the clock signal generated by the internal oscillator.

#### The Internal Oscillator (lines 21–25)

```verilog
SB_HFOSC osc_I (
    .CLKHFPU(1'b1),
    .CLKHFEN(1'b1),
    .CLKHF(clk)
);
```

Every digital circuit needs a **clock** — a signal that toggles between 0 and 1 at a fixed frequency, like a metronome. It is the heartbeat that synchronises all the flip-flops.

Many FPGA designs use an external crystal oscillator on the board, but the iCE40 UP5K has a built-in one called `SB_HFOSC` (Silicon Blue High Frequency Oscillator). This block is not something you write in Verilog — it is a piece of pre-built hardware ("hard IP") inside the chip. You just instantiate it (like plugging in a component) and connect its inputs and outputs.

- `.CLKHFPU(1'b1)` — "Clock High Frequency Power Up". Setting this to 1 turns on the oscillator's power. `1'b1` is Verilog syntax for "a 1-bit binary value of 1".
- `.CLKHFEN(1'b1)` — "Clock High Frequency Enable". Setting this to 1 enables the clock output.
- `.CLKHF(clk)` — The oscillator's output is connected to our `clk` wire.

The result: `clk` now toggles at approximately **48 MHz** (48 million times per second).

#### The Counter (lines 27–28)

```verilog
always @(posedge clk)
    cnt <= cnt + 1;
```

This is the core timing mechanism. Let's break it down:

- **`always @(posedge clk)`** means "every time `clk` has a **positive edge**" (transitions from 0 to 1). At 48 MHz, this happens 48 million times per second.
- **`cnt <= cnt + 1`** means "set `cnt` to its current value plus one". The `<=` is a **non-blocking assignment**, which is the standard way to assign values to registers in clocked logic.

So `cnt` counts up by 1 on every clock cycle: 0, 1, 2, 3, ... all the way up to 268,435,455, then wraps back to 0 and starts again (because it is 28 bits wide and overflows).

**Why is this useful?** Because different bits of the counter toggle at different speeds:

| Bit       | Toggles every         | Human-scale period     |
|-----------|-----------------------|------------------------|
| `cnt[0]`  | 1 clock cycle         | ~20.8 ns (way too fast to see) |
| `cnt[25]` | 2^25 = 33.5M cycles  | ~0.7 s on, ~0.7 s off = ~1.4 s cycle |
| `cnt[26]` | 2^26 = 67.1M cycles  | ~1.4 s on, ~1.4 s off = ~2.8 s cycle |
| `cnt[27]` | 2^27 = 134.2M cycles | ~2.8 s on, ~2.8 s off = ~5.6 s cycle |

The high bits give us slow, human-visible blink rates — for free, with no extra logic.

#### The PWM Signals (lines 30–32)

```verilog
assign rgb_pwm[0] = cnt[27] & (cnt[2:0] == 3'b000);
assign rgb_pwm[1] = cnt[26] & (cnt[2:0] == 3'b000);
assign rgb_pwm[2] = cnt[25] & (cnt[2:0] == 3'b000);
```

Each line creates a continuous connection (like wiring two things together — `assign` means "this wire always equals this expression").

Each PWM signal is the AND (`&`) of two things:

1. **A high counter bit** (`cnt[27]`, `cnt[26]`, or `cnt[25]`) — this determines the blink rate for that color. The bit is 1 for half the cycle and 0 for the other half, so it turns the color "on" for seconds at a time, then "off".

2. **`cnt[2:0] == 3'b000`** — this checks whether the lowest 3 bits of the counter are all zero. The lowest 3 bits cycle through 8 values (000, 001, 010, ... 111), so this condition is true for 1 out of every 8 clock cycles. This acts as **dimming**: even when the color is "on", the LED is only actually lit 1/8th of the time. It blinks so fast (6 MHz) that your eye perceives it as a dim steady light rather than flickering. This technique is called **PWM (Pulse Width Modulation)** and it is the standard way to control LED brightness in digital circuits.

Without the dimming, the LED would be painfully bright. With it, you get a gentle glow.

**The combined effect:** Each color blinks on and off at its own slow rate (determined by which high bit it uses), and while "on" it is dimmed to 1/8 brightness. Because the three colors have different periods, they go in and out of phase with each other, producing shifting color mixes (red, yellow, green, cyan, blue, magenta, white, off...).

#### The RGB LED Driver (lines 34–48)

```verilog
SB_RGBA_DRV #(
    .CURRENT_MODE("0b1"),
    .RGB0_CURRENT("0b000001"),
    .RGB1_CURRENT("0b000001"),
    .RGB2_CURRENT("0b000001")
) rgb_drv_I (
    .RGBLEDEN(1'b1),
    .RGB0PWM(rgb_pwm[0]),
    .RGB1PWM(rgb_pwm[1]),
    .RGB2PWM(rgb_pwm[2]),
    .CURREN(1'b1),
    .RGB0(rgb[0]),
    .RGB1(rgb[1]),
    .RGB2(rgb[2])
);
```

Like `SB_HFOSC`, `SB_RGBA_DRV` is another piece of hard IP built into the iCE40 UP5K. It is a dedicated LED driver circuit designed specifically to drive the onboard RGB LED safely and efficiently. You cannot just connect a regular FPGA output pin directly to this LED — you must use this driver.

The block has two parts:

**Parameters (the `#(...)` section)** — these are compile-time settings that configure the hardware:

- **`CURRENT_MODE("0b1")`** — selects "half-current" mode, which limits the maximum current the driver can supply. This protects the LED and keeps power consumption low.
- **`RGB0_CURRENT("0b000001")`** (and RGB1, RGB2) — sets each color channel to the minimum current level (4 mA in half-current mode). Higher values would make the LED brighter. The 6-bit value allows 64 brightness levels per channel.

**Ports (the `(...)` section)** — these are the runtime signal connections:

- **`.RGBLEDEN(1'b1)`** — master enable for the entire LED driver. Tied to 1 (always on).
- **`.RGB0PWM(rgb_pwm[0])`** — the PWM input for the red channel. When this signal is 1, current flows through the red LED; when 0, it does not.
- **`.RGB1PWM(rgb_pwm[1])`** — PWM input for green.
- **`.RGB2PWM(rgb_pwm[2])`** — PWM input for blue.
- **`.CURREN(1'b1)`** — enables the current reference. Tied to 1 (always on).
- **`.RGB0(rgb[0])`** — the actual output pin for red, connected to the module's top-level `rgb[0]` output.
- **`.RGB1(rgb[1])`** — output pin for green.
- **`.RGB2(rgb[2])`** — output pin for blue.

Think of it this way: the PWM signals are like light switches that rapidly flick on and off to control brightness, while the CURRENT settings are like a dimmer knob that sets the maximum brightness. Both work together.

## How blink.pcf Works

```
set_io rgb[0] 39
set_io rgb[1] 40
set_io rgb[2] 41
```

The PCF (Physical Constraints File) tells the toolchain which physical pin on the chip package each signal name should be connected to. The iCEBreaker board has its RGB LED wired to pins 39, 40, and 41 of the iCE40 UP5K's SG48 package. Without this file, the tools would not know where to route the `rgb` signals.

## How the Makefile Works

The Makefile automates the FPGA build process. Unlike compiling software (where you go from source code to an executable), building an FPGA design involves several distinct stages:

### The Build Pipeline

```
blink.v  -->  yosys  -->  PnR  -->  icepack  -->  iceprog
(source)    (synth)    (layout)   (bitstream)   (program)
```

1. **Synthesis (`yosys`)** — Reads the Verilog source and converts it into a **netlist**: a description of the logic gates and their connections. This is like compiling source code into assembly, but for hardware. The command `synth_ice40` tells yosys to target the iCE40 chip family.

2. **Place and Route (PnR)** — Takes the netlist and figures out *where* on the physical chip each logic element should go (placement), and *how* to connect them with the chip's internal wiring (routing). This is the step that has no equivalent in software — it is solving a complex spatial puzzle. The Makefile supports two PnR tools:
   - **arachne-pnr** (default) — the older, legacy tool
   - **nextpnr-ice40** (set `PNR=next`) — the newer, recommended tool

3. **Bitstream packing (`icepack`)** — Converts the placed-and-routed design into a **bitstream** (a `.bin` file): a binary blob that configures every switch and lookup table inside the FPGA.

4. **Programming (`iceprog`)** — Uploads the bitstream to the iCEBreaker board over USB, where it is written to flash memory. The FPGA loads it on power-up and becomes the circuit you designed.

### Common Commands

```
make            # run the full build pipeline (produces blink.bin)
make prog       # build (if needed) and flash to the iCEBreaker board
make sudo-prog  # same as prog but runs iceprog with sudo (for permission issues)
make clean      # delete all generated files
```

## Summary

The entire design is just three pieces of logic working together:

1. **Oscillator** generates a 48 MHz clock
2. **Counter** divides that clock down to human-visible speeds
3. **LED driver** uses different counter bits to blink red, green, and blue at different rates, with PWM dimming

No CPU. No software. No instructions executing in sequence. Just circuits running in parallel, all clocked by the same heartbeat.
